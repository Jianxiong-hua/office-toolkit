### 技术要点（踩坑）

- **mp4box 2.4.1 API 细节**：`appendBuffer` 需要 `MP4BoxBuffer.fromArrayBuffer(ab, fileStart)`（带 fileStart）；`DataStream.position` 是 protected，用公开的 `getPosition()`；avcC 盒经 `entry.avcC.write(stream)` 后取 `new Uint8Array(stream.buffer, 8, len)`（去掉 8 字节盒头）
- **mp4-muxer**：`addAudioChunkRaw(data, type, ts, duration)` 直接吃原始 AAC 样本，无需 EncodedAudioChunk；`fastStart:false` moov 置尾最省内存（2GB 场景）；自带 FileSystemWritableFileStreamTarget 留作将来流式写盘
- **倍速与音频互斥**：remux 的音频无法变速，`speed≠1` 时输出无音轨（UI 有提示）；减速不需复制帧——时间轴拉伸即真慢放
- **旋转烘焙**：tkhd matrix 非单位矩阵时用 DOMMatrix 推导 canvas 变换（移植参考项目算法），VideoFrame 的 displayWidth/Height 已含旋转信息
- **TS 控制流窄化陷阱**：在闭包内赋值的 `let` 变量（encoder/muxer），顶层使用处窄化为 null → `&&` 后变 never；解法是使用处 `as` 取回联合类型
- **mp4box 的 onSamples 是同步回调**：背压必须自建样本队列 + 泵循环，不能在回调里 await（挡不住 mp4box 的生产速度）；releaseUsedSamples 必须在样本真正 decode 之后调用，否则数据被释放
- 验证：tsc 通过；dev 下新页面 200、旧压缩页 200、首页含新工具卡片；**浏览器实测待用户执行**

### 修复：极速压缩「封装失败：输出为空」（2026-10-22 用户实测反馈）

- **根因 1（主因）**：`createFile()` 默认 `keepMdatData=false` 会**丢弃 mdat 数据**，onSamples 永远抽不出样本——必须 `createFile(true)`（mp4box 的 setExtractionOptions 里有 warn 提示，但只在运行时打印）
- **根因 2**：漏了 `setExtractionOptions(trackId, undefined, {nbSamples:1000})` + `start()`——mp4box 的 onSamples 只对注册过的轨触发，且 start() 才启动样本处理（已缓冲数据会被追溯抽取，后台泵先喂不丢）
- **根因 3**：帧率估算用「首批样本首尾 cts 差」在 B 帧下会被解码序重排带偏——改为**排序后取中位间隔**（实测 30fps 文件排序后间隔稳定 1001 tick）
- **验证方法（Node 可测 demux 半边）**：下载 flower.mp4（interactive-examples.mdn.mozilla.net，~1.1MB，avc1.64001f 960x540 30fps + mp4a 48k 立体声），跑 createFile(true)→分块 appendBuffer（必须 `MP4BoxBuffer.fromArrayBuffer(ab, fileStart)`，普通对象会报 DataView 错）→onReady→setExtractionOptions→start→onSamples：150 视频样本全带数据、2 关键帧、237 音频样本、avcC 50 字节（01 64 00 1f...）、matrix 单位矩阵。**教训：WebCodecs 半边浏览器外测不了，但 mp4box 链路可在 Node 全测**
- 修复后 tsc 通过、页面编译 200；**待用户重新浏览器实测**

### 再修复：mp4-muxer 时间戳红线（2026-10-22 用户二次反馈）

- 用户重试后错误变为通用「极速压缩失败」——样本抽取已通，死在封装侧。读 mp4-muxer 5.2.2 源码定位两条抛错红线（都被 catch 吞成通用文案，已加 `console.error` + UI 透传 details）：
  1. **`firstTimestampBehavior` 默认 strict：首块 DTS 必须为 0**。绝大多数视频轨带 edit list，首帧 cts≠0（测试文件 2002/30000s）→ 抛错。修：muxer 选项 `firstTimestampBehavior: "cross-track-offset"`（两轨同源时钟，公共基准偏移，不破坏音画对齐）
  2. **DTS 必须单调递增**。B 帧下编码器按解码序吐块、chunk.timestamp 是展示时间戳（0,40,20…）→ 抛错。修：自维护 videoDecodeClock 估 DTS，改调 `addVideoChunkRaw(data, type, pts, duration, meta, pts-dts)`；顺带兜底 `chunk.duration` 可能为空的问题（addVideoChunk 内部直接用 sample.duration，无法覆盖，必须走 Raw 版）
- 教训：WebCodecs 编码块是「解码序 + 展示时间戳」，与 MP4 封装器的 DTS 模型差一个 compositionTimeOffset；浏览器外无法复测，只能读库源码 + 用户实测闭环

### 三修复：VideoDecoder「Decoding error.」（2026-10-22 用户三次反馈）

- 用户三次报错，UI 透传的 details 显示 `Decoding error.`——VideoDecoder 运行时解码失败。**Node 侧已证明 demux 无罪**：分块边抽边放 vs 整文件喂逐字节一致（test-pipeline.js）；sample0 为标准 AVCC（长度前缀 0x322 + SEI NAL）；appendBuffer 每次触发 processSamples（流式抽取真实流动）
- 修复 1（最可能主因）：**decoder.configure 不再传 codedWidth/codedHeight**——sample entry 的宽高可能是显示尺寸，与 SPS 编码尺寸（含 crop，如 1088 裁 1080）不一致时 Chrome 解码阶段才炸；省略后由解码器从 SPS 推导
- 修复 2：**硬件解码失败自动软件重试一次**（`sawDecodeError` 标志 + 外层 run("prefer-software")），覆盖异常 profile/10bit/驱动兼容问题
- 修复 3：倍速丢帧的 grid 取整在 speed=1 浮点边界会误杀帧（如 0.0667s*30fps=2.001 与 3.003 间丢帧）→ 改为「距上一保留帧间隔 < 半个帧间隔才丢」
- 诊断：console 打印 decoder 完整配置（codec/track 尺寸/description 十六进制）、前 3 个送解码 chunk（type/ts/size/字节头）、解码器与编码器错误对象——浏览器侧问题现在可自证
- 另确认两个「以为有其实没有」的坑：`releaseSample` 只置空 sample.data 引用不动底层缓冲（音频 data 直接给 muxer 持有是安全的）；`getSample` 的 data 是 memcpy 独立拷贝（decode 前 release 也安全）

### 四修复：B 帧金字塔抽帧导致解码失败（2026-10-22，根因锁定）

- **诊断方法（关键转折）**：搭临时诊断页 `/debug-webcodecs`（自动下载测试视频 + 后来加「诊断我的文件」拖入），跑只解码最小链路。用户两个真实文件（斗罗大陆 53MB avc1.640032 1920x1080 / 一人之下 24MB avc1.640028 1920x798）**全量解码 40376/40376、34129/34129 全部正常**——证明 demux/配置/chunk 构造全对，问题在工具侧
- **真根因**：倍速抽帧逻辑跑在**解码前**，按**解码序**处理。B 帧 cts 小于前一保留帧 → `outTs - lastKeptTs < 间隔` → **B 帧被丢**。普通 IPB 丢 B 帧无事，但 **x264 压制片源（用户这两个动画 rip）带 B 帧金字塔，被丢的 B 帧是后续 B 帧的参考帧 → 后续帧解码失败 → "Decoding error"**。硬件/软件都炸是因为码流完整性损坏，与硬件无关（所以软件重试也没救）
- **修复**：抽帧从解码前移到**解码输出端**——输出帧按展示序到达、时间戳单调，按间隔保留绝对安全；解码侧喂全量帧保住参考链。`minOutputIntervalUs = (1e6/outFps)*0.5`（speed=1 时保留全部帧）
- **教训**：① WebCodecs 输入侧丢帧必须保证不破坏参考链，输出侧（展示序）丢帧才安全；② 诊断页「只解码」与工具全链路的差异（丢帧/编码）正是定位关键——测试视频碰巧无 B 金字塔所以早期"偶现通过"；③ 别再用硬编码错误信息（"Decoding error."）包住原始错误，会掩盖真实原因

### 六修复：固定码率越压越大 + 收尾阶段假死（2026-10-23 用户实测反馈）

- **体积翻倍**（142MB → 294MB，默认参数）：WebCodecs 是**固定码率编码**（用到目标为止，不像 CRF 够用就好），bpp 反推的 2Mbps 目标远高于该片源实际 ~1Mbps → 越压越大。修复：目标码率取 `min(bpp反推值, 源视频码率 × 档位折扣)`；源码率 = `文件大小×8/时长 − 128k(音频余量)`，时长由页面 `readVideoMeta` 传入（fastCompressVideo 第 4 参）；折扣 high 0.85 / standard 0.6 / strong 0.4；下限 300k、上限 24M。用户文件标准档预期 520kbps ≈ 75MB（-47%）
- **二三阶段慢**：解码→编码间无背压，整部片子的帧瞬间堆进 VideoEncoder 内部队列，编码工作量全攒到 flush 才计费。修复：decoder.output 同步回调只入队，新增**编码泵**（异步，按 `encodeQueueSize > 8` 背压）；flush 顺序改为「样本排空 → decoder.flush → 编码队列排空 → encoder.flush → finalize」；进度改**帧数制**（encodedFrames/估算总帧，时长已知时比字节制平滑）；阶段文案「硬件解码中」→「硬件解码编码」
- 结果区新增码率显示；输出大于输入时显示「增大 X%」并提示试强压缩档
- 验证：tsc + 页面 200；**待用户复测**（重点看默认参数下体积是否小于源文件、第一阶段是否为连续进度）

### 七修复：缩放变裁剪 + 拖动卡顿 + 旋转尺寸源错误（2026-10-24 用户实测反馈）

- **宽高比失真（严重）**：canvas 路径用 `drawImage(frame, 0, 0, srcW, srcH)` 把帧按**源尺寸**画进**目标尺寸**画布——从来不是缩放而是**裁剪**，选任何分辨率档输出都是左上角裁切（比例怪异）。另：尺寸来源用 `videoTrack.video.width/height`（sample entry，旋转视频上可能是显示尺寸而非 coded 尺寸）不可靠
- **修复**：输出尺寸改为**首帧 `frame.codedWidth/Height`（唯一真相）**驱动——configureAll 只配解码器（codec+description，不传尺寸），新增 `ensureEncoded(frame)` 在首帧时定尺寸+建 muxer+配 encoder；非旋转缩放用九参数 `drawImage(frame,0,0,cw,ch,0,0,outW,outH)` 真正缩放；旋转路径 `rotationTransform(matrix, codedW, codedH, outW, outH)`（矩阵同时做旋转+缩放）
- **音频缓冲**：muxer 改首帧创建后，此前到达的音频样本进 `audioPreBuffer`，建好 muxer 后补入（避免开头音轨丢失）
- **拖动进度条卡顿**：编码器关键帧间隔不受控。修复：每 2.5 秒（outFps×2.5 帧）强制 `encode(frame, {keyFrame:true})`
- 验证：tsc 通过、页面 200；**待用户复测**（重点：分辨率缩放后的比例、旋转手机视频方向、拖动进度条响应）

### 八修复：懒初始化顺序回归 + 耗时显示（2026-10-24）

- **回归（我自造）**：重构把 encoder/muxer 改首帧懒初始化后，编码泵的守卫句 `if (!enc || enc.state !== "configured") break;` 在**首帧时 encoder=null 直接 break**，而泵的 `finally` 会把队列里所有帧 close 丢弃——每帧都被如此对待，muxer 从未创建 →「封装失败：输出为零」。修复：`ensureEncoded(encodeQueue[0])` 移到状态检查**之前**并包 try/catch→fail；收尾处的 enc 捕获改实时读取（防止捕获时编码器未建、漏掉内部队列与 flush）
- **教训**：懒初始化调用点必须在所有「未初始化就退出」的守卫句之前；泵/队列模式的 `finally` 清理会把提前 break 变成静默数据丢失
- 新增：结果区显示**处理耗时**（`performance.now()` 打点于外层，含硬件→软件重试总时长；<60s 显示秒、以上显示分+秒）；结果类型加 `elapsedMs`

### 九修复：isRotated 矩阵解包顺序（真·比例错误根因，2026-10-24）

- 用户截图实锤：源 1920x804（横屏）→ 输出 816x1920（竖屏），宽高被对调
- **根因**：MP4 tkhd 矩阵是 9 元行主序 `[a,b,u,c,d,v,x,y,w]`（16.16 定点），我按 `[a,b,c,d,e,f]` 直接解包——单位矩阵前 6 元 `[1,0,0,0,1,0]` 解出的 `d=0`（实际是 `c`），**单位矩阵判定永远失败 → 所有视频都被当成旋转视频** → 宽高对调。正确解包是 `[a,c,e,b,d,f]`（`rotationTransform` 一直是对的，只有 `isRotated` 写错）。此 bug 从首版就存在，之前几轮「比例不对」的修复没打中真凶
- 顺修三处：① 尺寸与绘制改用 `frame.displayWidth/Height`（已应用 SPS 裁切，1920x816 coded → 1920x804 画面）而非 coded 尺寸；② `encoder.configure(config)` 改用自建 config（不再用浏览器规范化的 `support.config`，后者可能导致 bitrate 不生效、输出 121MB 远超 1.82Mbps 目标）；③ 页面 `savedRatio` 去掉 `Math.max(0,…)` 钳制，输出变大时能如实显示「增大 X%」
- 教训：MP4 矩阵的 2x3 线性部分在 9 元数组里不连续（a=m0, b=m1, c=m3, d=m4），任何直接 `slice(0,6)` 后顺序解包都要先确认布局
- **教训**：同一文件的多个编辑必须串行；并行批次只能放不同文件。已并入 MEMORY.md「结构性陷阱」
- **附带发现**：PowerShell 管道会把 curl 的 UTF-8 输出按 GBK 解码，导致中文 grep 静默匹配失败——验证页面中文内容必须 `curl -o 文件` + node 读文件判断，不能直接管道 Select-String
