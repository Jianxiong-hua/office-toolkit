### 一、代码审查发现的 bug 与修复

- **页面 `handleConvert` 缺 `meta` 依赖**：`useCallback([file, options])` 里读 `meta?.duration`，
  选完文件时 meta 还是 null，回调被固化 → `sourceDurationSec` 永远 undefined，
  源码率封顶与帧数制进度双双失效。补 `meta` 到依赖数组。
- **`chunk.duration` 与输出帧间隔不是一套时间轴**：送解码的 duration 是「源帧时长/speed」，
  而抽帧后的实际帧间隔是它的 speed 倍。采信 `chunk.duration` 会让 DTS 持续落后 PTS，
  ctts 越积越大 → 倍速输出拖动进度条卡死。改为 `duration = ptsDelta`（相邻块 pts 差）。
- **输出帧率算错**：`outFps = srcFps / speed` 是错的。倍速是「抽帧 + 时间轴压缩」，
  时长和帧数同比例减少 → 帧率不变；慢放才是 `srcFps × speed`。
  改为 `srcFps × min(1, speed)`（影响码率、关键帧间隔、总帧数估算）。
- **截取起点把关键帧本身跳掉了**：解码前有 `if (tsSec < startSec) continue`，
  而起点关键帧的 cts 必然早于起点 → 解码器收到的第一个 chunk 是 delta 帧 → Decoding error。
  改为只按 `decodeFromNumber`（起点前最近关键帧）过滤，起点前的帧照喂、输出端按负时间戳丢弃。
- **B 帧下解码起点回退过远**：`cts` 在解码序上非单调（实测某片源 68 处重排），
  「遇到第一个 `cts >= startSec` 就 break」会提前中断，把起点误判到片头。
  改为整表扫完，取 `cts <= startSec` 的最后一个关键帧。
- **编码队列无跨阶段背压**：解码比编码快，自建 `encodeQueue` 无上限 → 长片内存爆。
  加 `ENCODE_QUEUE_FRAMES` 上限，`pumpVideo` 同时等 `decodeQueueSize` 与 `encodeQueue.length`。
- **格式校验失败后仍读完整文件**：`run` 拆成 `run`/`runPipeline`，`finally` 置 `aborted`，
  读取循环响应中止标志。
- **取消不释放编解码器**：抽出 `closeCodecs()`，`fail()` 与 `cancelReject` 共用。
- **moov 在尾部的 MP4 曾整体读入并一次性 flush** → 页面无响应：见下方架构重构。
- 页面层：转换中禁用「重新选择」；拖拽区删掉无效的 `video/mp4v-es`。

### 二、架构重构：mp4box 只解析元数据 + 样本随机读

**动机**：用户片源是 2.75GB 的 MP4，`ftyp + free + mdat(2.74GB) + moov(4.6MB，在末尾)`。
旧实现必须顺序读完整文件才能拿到 moov，且 mp4box 为抽取样本会保留整个 mdat。

**新架构**：
1. `createFile(false)`（不保留 mdat），先喂文件头 256KB；
2. 未解析出 moov 就按顶层 box 顺序跳读——遇到 `mdat` 直接跳过，只读 `moov` 喂进去；
3. `onReady` 后 `getTrackSamplesInfo` 拿完整样本表（含 offset/size/cts/is_sync）；
4. 样本数据按 `sample.offset` 用 `File.slice` 批量随机读（每批 ≤128 样本 / 4MB，预读下一批与解码重叠）；
5. 音频独立泵，按 offset 读样本数据后 `addAudioChunkRaw`。

**实测**：2.75GB 片源 **349ms / 只读 4.86MB（0.17%）** 拿到 170656 视频样本 + 333766 音频样本。

**验证方法（Node 侧，可复现）**：`file.slice` 换成 `fs.readSync` 按偏移读，喂 `MP4BoxBuffer.fromArrayBuffer(buf, fileStart)`；
`getTrackSamplesInfo` 的 offset/size 读出的字节与 `onSamples` 给出的数据**逐字节一致**；
`moov` 单独喂（fileStart=moov 偏移）能触发 onReady，此前只有 ftyp/free/mdat 头 + moov 也能解析。

### 三、音频整条轨解码失败（PCE 声道配置）

- **现象**：输出视频正常，音频 4550/4550 帧 ffmpeg 全部报
  `channel element 0.0 is not allocated`。
- **根因**：源音轨的 `AudioSpecificConfig` 是 25 字节，`channelConfiguration=0`
  （声道布局写在帧内 PCE 里，PCE 中还嵌了 "Lavc58.9.100" 字符串）；
  而 mp4-muxer 按 `numberOfChannels` 只生成 2 字节的 `11 90`（stereo）。
  数据原样复制但解码配置不符 → 解码器按 stereo 解 PCE 帧全部失败。
- **修复**：新增 `extractAudioSpecificConfig()` 从 `stsd → esds → DecoderSpecificInfo`
  取完整 ACS，在第一块 `addAudioChunkRaw(data, type, ts, dur, { decoderConfig: { description: acs } })` 里传给 muxer
  （mp4-muxer 的 `createSampleForTrack` 会用 `meta.decoderConfig` 覆盖，`esds` 从 `track.info.decoderConfig.description` 取）。
- **验证**：用源音频数据 + 源 ACS 重新封装 400 帧，ffmpeg 解码成功（wav 4.9MB、0 错误）；
  同数据用 stereo 配置解则 400/400 全错。

### 四、性能调优（1080p 7040 帧，57s）

- **解码/编码都显式 `prefer-hardware`**：`no-preference` 下浏览器遇到硬编不支持的配置
  （如 4K 需要的 High 5.1）会静默退软编，`isConfigSupported` 仍返回 supported。
  改为先探 `prefer-hardware`、不支持再回退 `no-preference`。4K 场景 28fps → 42fps；
  1080p 两侧都命中硬编，稳定 126fps。
- **编码泵等槽位改为事件驱动**：原来 `while (encodeQueueSize > N) await sleep(2)`，
  setTimeout 实际抖动 2~4ms，每帧赔一次把 160fps 拖到 ~100fps（表现为前期 160fps、后期掉速）。
  改为 `encoder.output` 回调唤醒 + 单个 50ms 兜底看门狗。
- **消除每帧分配**：`isRotated(trackMatrix)` 每帧解包矩阵生成新数组 → 预计算成常量；
  `Math.round(outFps * 2.5)` 每帧算 → 配置阶段预计算 `keyFrameInterval`。
- `ENCODE_QUEUE_LIMIT` 8 → 24；`SAMPLE_BATCH` 64 → 128（减少 IO 次数与批间停顿）。
- 结论：1080p 7040 帧 56~57s（≈5 倍速实时），继续压缩只剩降 `latencyMode` 到 realtime 这类画质取舍，未做。

## 九、视频压缩 / 视频转 GIF 提速（同日晚，独立提交，版本 1.11.1）

对应提交：「视频工具提速：新增 GIF 极速模式、压缩多线程」

### 一、A 多线程 ffmpeg core

- 新增 `public/_headers`（Cloudflare Pages 读取，`next build` 会输出到 `out/_headers`）：
  COOP `same-origin` + COEP `require-corp`，使 `SharedArrayBuffer` 可用、`crossOriginIsolated=true`。
  站点唯一跨域资源是 unpkg 的 ffmpeg core（已带 `Cross-Origin-Resource-Policy: cross-origin`），pdfjs 走本地模块，不受 COEP 影响
- `ffmpeg.ts`：`ensureLoaded({ multiThread })` 按调用方要求选 core（`@ffmpeg/core-mt` 的 core/wasm/worker 三件套，
  全部 `toBlobURL`），类型不符时先终止旧实例再重载；新增 `getFfmpegCoreMode()` 供结果面板标注
- **实测结论：core-mt 不能用于 GIF 的 `split+palettegen+paletteuse` 滤镜链**。同一 750 帧素材：
  单线程 155.7 秒完成；多线程（16 核）295 秒仍停在「分析视频帧」阶段（更早一次跑到 918 秒未出帧）。
  故 `gif.ts` 传 `forceSingleThread: true`，GIF 页也显式 `ensureLoaded({ multiThread: false })`（双保险，避免先加载多线程再重载）；
  视频压缩仍走多线程（滤镜链只有 scale/setpts，主要开销是 x264）

### 二、B GIF 极速模式（WebCodecs）

- 新增 `src/lib/video/fastGif.ts`：mp4box 跳读 moov → `VideoDecoder` → OffscreenCanvas 缩放/旋转
  → 按 fps 网格抽帧 → 每帧 `quantize`/`applyPalette` → gifenc 流式写入。
  仅 MP4/MOV + H.264，不满足时抛错引导关闭开关（不做静默回退）
- 页面新增「极速模式（WebCodecs 解码）」开关：文件支持时默认勾选，不支持时禁用并说明原因
- 逐项实测（480×202、128 色、15fps、2112 帧）：

  | 改动 | 每帧 | 总耗时 |
  | --- | --- | --- |
  | 首版（每帧量化 + 硬解 + willReadFrequently） | 48.3 ms | 102.1 秒 |
  | 每 16 帧复用调色板 | 24.7 ms | 52.1 秒 |
  | 解码改 `prefer-software` | 16.3 ms | 34.4 秒 |
  | 关闭 `willReadFrequently` | 13.7 ms | 约 29 秒（按 750 帧实测外推，全片未实测） |

- 三条反常识结论（已写进代码注释，防止以后「顺手优化」回去）：
  - `gifenc` 的 `quantize` 是绝对瓶颈（约为 applyPalette+LZW 的 7 倍）；降采样无收益
    （成本取决于颜色分布而非像素数），只能靠复用调色板，16 帧后收益已饱和（16→30 帧只再省 7%）
  - **软件解码快于硬件解码**：硬解帧是 GPU 纹理，`drawImage` 到 CPU 位图要额外回读（16.5 ms）；
    软解后成本转移到 `getImageData`（7.4 ms），合计仍省 8.9 ms/帧
  - **`willReadFrequently: true` 在此场景是负优化**：`getImageData` 从 7.5 ms 降到 3.3 ms 全靠关掉它
    （配合软解后帧本就在内存里，走 GPU 后端的回读量只有输出尺寸量级）
- `fastCompress.ts` 仅把 `isRotated` / `rotationTransform` 改成导出供复用，逻辑未动

### 三、C 兼容模式滤镜微调
