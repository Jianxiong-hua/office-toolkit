### 二、语义设计与踩坑（可复用）

- **位模式统一用 `bigint` 表示**（浮点也是），进制换算、位翻转、移位、字节序全部落在同一套逻辑上；64 位整型必须 BigInt，`Number` 超过 2^53 静默失真
- **BigInt 字面量（`0xFFn`）在 tsconfig `target` < ES2020 时过不了 `tsc`**：报 TS2737 满天飞。改 `target` 只影响类型检查（产物由 Next/SWC 按浏览器目标编译），比把 50 处字面量改成 `BigInt(1) << BigInt(n)` 划算
- **「非十进制输入按位模式、十进制输入按数值」是这套工具的核心规则**：初版让有符号类型一律按数值解析，`0xFF` 选 `s8` 会被判 255 溢出——而程序员的预期是 -1。统一成位模式语义后 `0xFF`→-1、`0x80`→-128、`0x1FF`+`u8` 仍报溢出并建议 u16
- **float32 十进制输入的精度必须显式暴露**：`0.1` 实际存成 `0x3DCCCCCD`（0.10000000149011612），用 `Math.fround` 取存储值再与输入比对，不一致就提示「实际存储值 = …」
- **溢出建议只能给更宽的类型**：初版出现「9223372036854775808 超出 s64，可用 s64」的自我指涉提示
- **文本与结果必须始终一致**：切换类型装不下时按新位宽截断位模式、**并把输入框改写为十六进制**；点翻转、点移位同样改写。否则下次任何重解析都会把用户的操作悄悄回滚
- **`float` 与 `int` 都走「逻辑移位」**：若按算术右移，`s8` 的 `0x80 >> 1` 得 `0xC0` 而 `u8` 得 `0x40`，同一按钮在切类型后含义就变了
- **字节串判定要收紧到「每段正好 2 位、至少两段」**：宽松版会把 `1010 1010` 这种分组二进制误读成 4 个字节 `10 10 10 10`
- **自动识别字节串的缺陷（本轮发现并修）**：`detectRadix` 对 `00 00 80 3F` 返回十进制（含空格不满足纯数字正则），而字节串分支要求 `radix === 16` → **默认「自动」模式下字节串路径从不生效**（只有手动选十六进制才通），粘字节串会报「含非法字符 F」。修法：含空格且全为十六进制字符 → 16
- **开关的可用性本身要能表达语义**：用户问「float 模式切大小端结果一样，这对吗」——因为非字节串输入下字节序本就不参与计算。与其写规则说明，不如按输入把按钮置灰
- **PowerShell 没有 `tail`**：`... | tail -12` 直接报「术语不被识别」，用 `Select-Object -Last 12`
- **纯函数验证的廉价路径**：`npx tsc <file> --outDir .tmp-check --module commonjs --target es2020` 后用 node 跑断言脚本，不引测试框架；跑完删掉临时目录（测试卫生约定）

## 新增「RAW 图查看」工具（单张 + 批量）

对应提交：「新增「RAW 图查看」工具…」（定位靠日期 + 标题，本文不记 hash）

### 一、决策链（用户逐条拍板，未替他选）

1. 输入形态：**裸像素数据**（不解析 CR2/NEF/ARW/DNG，不引 libraw-wasm）
2. 位深：只做**未打包**（8 bit 1 字节/像素，10/12/14/16 bit 2 字节/像素）；字节序可选；10/12/14 bit 提供**低位/高位对齐开关**
3. 不做 BLC（黑电平校正）
4. gamma 三档：线性 / 2.2 / sRGB（默认线性）
5. 去马赛克：**Malvar-He-Cutler**（不做双线性可选）
6. 顺序：~~先 8bit 再去马赛克~~ → **先 DN 域插值再量化**（用户看过代价后改的）
7. 预览要缩放（−/+、适应窗口、1:1、拖动平移）
8. 默认参数：1920×1080、12 bit、RGGB、线性
9. 批量：改造同一页面（不另起工具）；**默认全内存 ZIP，超过阈值才要求选目录**；阈值 = 张数 ≤ 50 **且** 预估 ≤ 200 MB；非 Chromium 超阈值只提示分批/换浏览器；参数共用；失败跳过；命名 `原名_demosaic.png`

### 二、技术要点（可复用）

- **MH-C 核必须与官方整数公式逐项核对**：IPOL《Malvar-He-Cutler Linear Image Demosaicking》给出 `R = [F(i,j±2) - 2*(六个对角+上下±2) + 8*(左右±1) + 10*F(i,j)] / 16`，4 个核的每个非零项都能对上；系数统一 ×2 成整数（原始核含 0.5 / 1.5），分母 16
- **线性场解析解是核正确性的硬判据**：MH-C 在线性渐变上可被核精确还原，实测 flat / x / y 渐变误差 **0**、对角 1。若 `dx`/`dy` 索引写反或 G 相位下「R 在同行还是同列」判断反了，x 或 y 渐变会立刻暴露——比 PSNR 好定位得多
- **合成图上 MH-C 的 PSNR 反而低于双线性约 2 dB**（24.7 vs 27.0），不是 bug：合成图通道不相关且高饱和，MH-C 的负瓣在饱和边缘过冲、被 clamp 后误差变大。IPOL 官方数据里 MH-C 对 Peppers 也只领先 0.19 dB；它的真实优势是伪彩/拉链纹更少。**验收标准因此改为「线性场精确 + 错误排列显著劣化（9.47 dB）+ 人工观感」**，不要迷信「PSNR ≥ 30 dB」
- **canvas 必须常驻挂载**：放在 `preview ? <canvas/> : <占位/>` 分支里时，生成那一刻 canvas 还没渲染、`ref.current` 为 null，像素写不进去。改为常驻 + 无数据时 `hidden`
- `new ImageData(rgba, w, h)` 在 TS 严格模式下不接受 `Uint8ClampedArray<ArrayBufferLike>`，用 `ctx.createImageData()` + `data.set()`
- **Ctrl + 滚轮在网页里是整页缩放**：自己接管会让人以为「整个网页被缩了」（用户实测反馈），已连同提示一起删除，缩放只走按钮
- **单张与批量共用 `convertOne`**，只在输出环节分叉（`zip.file()` vs `writeBlobInto()`），避免两套解码逻辑漂移
- **批量用独立隐藏 canvas 做 PNG 编码**，不占预览 canvas，转换完成后预览仍停在用户选的那张
- **每张之间 `await setTimeout(0)`**：同步卷积期间进度与「取消」完全无响应，必须让出主线程
- ZIP 用 `compression: "STORE"`（PNG 已压缩，重复 deflate 只烧 CPU）
- 目录写入直接复用 `lib/fs/save.ts` 的 `supportsDirectoryPicker` / `pickDirectory` / `ensureUniqueSubdirectory` / `writeBlobInto`，与「视频提取图片」同一套
- **内存账**：1080p 单张瞬时约 16 MB（raw 4.1 + mosaic 4.1 + RGBA 8.3），PNG 成品 1~4 MB 常驻；50 张 4K 可达 300~500 MB，所以只看张数不够，必须同时卡体积
