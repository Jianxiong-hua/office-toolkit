### 一、决策过程（全部由用户逐条拍板）

| 议题 | 用户选择 | 被否方案 |
| --- | --- | --- |
| 提取规则 | 起止时间 + 每隔 N 帧取 1 张（N=0 每帧，跨步 = N+1） | fps 输入、指定时间点列表 |
| 落盘 | 目录写入为主 + ZIP 兜底（ZIP 限 300 张） | 仅 ZIP（JSZip 全内存） |
| 图片格式 | PNG/JPEG 下拉，默认 JPEG 0.92 | WebP（Safari 静默回退 PNG） |
| 帧数预警 | 软预警（>500 张），不阻断 | 强制确认、硬上限 |
| 合成引擎 | 仅 WebCodecs + mp4-muxer → MP4 | ffmpeg 双路径、仅 ffmpeg |
| 合成尺寸适配 | 输出尺寸四档 + 黑边/裁切二选（默认原始+黑边） | 仅第一张尺寸、拉伸 |
| 节奏模式 | 每张 N 秒 + 每张 1 帧并存 | 只做一种 |
| 排序 | 文件名自然排序 + 上下移动 | 拖拽排序 |
| 大规模 | Chromium 流式写盘，其他内存模式限 5 分钟 | 统一内存 + 硬上限 |
| 兼容模式大文件 | **200MB 硬上限**（后期追加） | 2GB + WORKERFS 挂载 |
| 只解 I 帧加速 | **明确否决**，不准再考虑 | — |

### 二、实现要点

**视频提取图片**

- `src/lib/video/extractFrames.ts`（快路径）：mp4box 跳读 moov → 样本表 → 关键帧对齐 fromIdx → `VideoDecoder`(prefer-software) → 输出回调按**展示序计数取模**（`rangeIndex % step === 0`）→ canvas 旋转烘焙 → `convertToBlob` → sink
  - `readFastVideoInfo()` 返回 `times: Float64Array`（每帧展示时间），页面据此**精确**预估张数
  - `pending` promise 链串行化导出：保证顺序、不堆内存，且 VideoFrame 必须等 draw 完才能 `close()`（先 close 后 draw 会 use-after-close）
- `src/lib/video/ffmpegSequence.ts`（兼容路径执行器）：`writeFile` → `exec` → `listDir("/")` → 逐个 `readFile`/删 → onFile；取消走 `cancelReject` + `cancelConversion()`（terminate 后 exec 永不 resolve，只能 race）
- `src/lib/video/extractFramesCompat.ts`：参数 `-y -ss -t -i -vf select=not(mod(n\,step)) -vsync 0 -an [-q:v] frame_%06d.<ext>`
- `src/lib/fs/save.ts`：`showDirectoryPicker` / `ensureUniqueSubdirectory`（重名自动 `-2`）/ `writeBlobInto`；另含 `showSaveFilePicker` + 可写流给合成工具

**图片合成视频**

- `src/lib/video/imagesToVideo.ts`：逐张 `createImageBitmap` → canvas 按适配绘制 → `new VideoFrame(canvas, {timestamp,duration})` → `encoder.encode` → 立即 close；背压 `encodeQueueSize > 8`
- Chromium：`FileSystemWritableFileStreamTarget`（`fastStart: false` 才能顺序写盘）；否则 `ArrayBufferTarget`
- 码率 = bpp × w × h × fps，四档 0.25/0.12/0.06/0.03，上限 80 Mbps

### 三、实测结论（重要，都是踩出来的）

**1. 提取速度模型（1080p/25fps 实测两组）**

| 参数 | 出口侧 | 解码 | 墙钟 |
| --- | --- | --- | --- |
| 每隔 300 帧 | draw 1 + encode 28 + write 136 = 165 ms/张 | 301 帧 × 2.9 ms ≈ 860 ms | 1028 ms/张 |
| 每隔 10 帧 | draw 1 + encode 33 + write 95 = 129 ms/张 | 11 帧 × 2.9 ms ≈ 32 ms（被出口侧隐藏） | 130 ms/张 |

结论：`单张耗时 ≈ max(出口侧 ~130 ms, 需解码帧数 × 2.9 ms)`；拐点约 44 帧（1080p/25fps ≈ 1.8 秒）。
**耗时由片段时长决定，与导出张数几乎无关**——增大「每隔 N 帧」只省磁盘不省时间。
早期把「均速递增」误判为写盘劣化，加阶段计时后证伪。

**2. 兼容模式（wasm）在本机完全不可用**

- core 实际为 **FFmpeg 5.1**（`libavcodec 59.37.100`），`-fps_mode` 不该用（换 `-vsync 0`）
- 2.13GB / 3635 秒 MKV 逐帧解码要几十分钟，必然撞 30 分钟 exec 超时；1000 秒片段 41 秒只走 3%
- 期间界面只显示「正在准备…」→ 补 `ffmpeg.on("progress")` + `time/clipDurationSec` 折算解码百分比
- 用户最终决定：**兼容模式只接 ≤200MB**，超过一律拒绝并提示先转 MP4

**3. 编解码格式坑**

- `.mp4` 不等于 H.264：用户的 mp4 是 `hev1`（HEVC）→ 快路径拒绝是对的，但初版提示没写原因，已把原因带进错误文案
- H.264 除 `avc1` 还有 **`avc3`**（参数集在码流里），已兼容；`avc3` 不能传 decoder description

**4. 合成画质（用户反馈「压缩得没法看」→ 已修）**

- 根因：初版把 bpp 固定 0.025（1080p30 仅 1.55 Mbps）且**没有画质选项**；「静态画面低码率够用」的假设被证伪——观众看的是每帧细节
- 修正：四档，默认高档（1080p30 7.5 Mbps）；4K 极高档需 62 Mbps，因此上限提到 80 Mbps
- 体积估算给区间（目标码率×时长 ~ ×1.4）：实测 228 张 / 每张 1 帧 / fps 10 / 2.49 Mbps，估 6.8 MB 实际 8.05 MB（+18%）——每张一帧时**每帧都是场景切换**，编码器基本全出 I 帧，压不到目标码率

### 四、其他踩坑

- `@ffmpeg/ffmpeg` 在 worker 出错时 `reject(data)`，`data` 是**字符串**而非 Error → `e.message` 取不到，页面只剩无信息量兜底文案。必须 catch-all 转成 `AppError` 并带 `stderr 尾部`
- 日志采样上限 30 条恰好把错误行吞掉 → 改为全量打印 stderr（单行截 300 字符），环形缓冲留 60 条给错误详情
- `File System Access` **只暴露目录名，给不了绝对路径**；界面只能显示「父目录名 / 子目录名」，并向用户说明原因
- 子目录**懒创建**（首次写盘时创建），快路径失败回退时不会留下空文件夹
- 运行中用局部变量定格扩展名，避免中途改格式导致同批文件扩展名不一致
